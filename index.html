Software Configuration Management & Testing

Managing every piece and part of what we build — code, documents, tests — so teams can change software without losing control of it, and test it so it keeps working.

Based on the class lecture by Andrew Joseph Ramos

Overview

Software Configuration Management (SCM) is the process of managing all the pieces and parts of the artifacts produced during software development and support. Artifacts are code, documentation, tests, and so on.

More than versions

SCM is not just keeping multiple versions of code or documents. It also involves planning and tools.

Guidelines & standards

The IEEE Guide to SCM (Std. 1042–1987) and NASA’s SCM Guidebook are examples. SCM is also a key process of the SEI’s Capability Maturity Model (CMM).

Maturity levels

CMM defines an increasing series of levels for an organization. The higher the level, the better the process, but reaching each level is expensive and time-consuming.

Learning objectives

  1. Describe SCM in the context of the software engineering process.
  2. Identify the models included in the configuration management framework.
  3. Describe the activities of a software build and integration process.
  4. Identify several automation tools for configuration management.

Why we need SCM

👥

Many people, many changes

Several people work on software that is continually updating. Versions, branches and authors multiply, and teams are often geographically distributed and working concurrently.

🔄

Change is constant

User requirements, policy, budget and schedule all change and must be accommodated.

💻

Many environments & costs

Software may need to run on various machines and operating systems. SCM also helps control the cost of making changes to a system.

SCM activities

  1. Understand the policy, process activities and the resulting artifacts to be managed.
  2. Define the framework used to manage those artifacts.
  3. Bring in the tools needed to facilitate the management.
  4. Train the team and ensure the agreed process is practiced and followed.

SCM participants

Four roles take part in SCM. Select a role to see what it is responsible for.

Project Manager

  • Ensures the product is developed on schedule.
  • Monitors the progress and issues in the SCM process.
  • Makes sure processes and policies are followed.

Configuration Manager

  • Responsible for identifying configuration items.
  • Ensures the team follows the SCM process.
  • Approves or rejects change requests.

Developer

  • Changes the code per change request and maintains the configuration of the code.
  • Checks for changes and resolves any conflicts.

User

  • Should have a basic understanding of key SCM terms and processes to ensure proper usage, e.g. having the latest version of the software.

SCM parts: what gets managed?

Which pieces need managing depends on the process. A conservative organization building large, complex software may use full waterfall with inspections after every major activity. A small Agile organization may emphasize only a few activities, such as requirements and coding. Either way, the parts fall into three groups.

1. Artifacts

  • Requirements specification
  • Design specification
  • Source code
  • Executable code
  • Test cases

Source code may include logic or pseudocode, database tables and user screen scripts.

2. Policy impact

A business policy can reshape how artifacts are controlled. For example, letting customers stay on French version 2 instead of migrating to version 3, and even update to French version 2.1, forces a development policy and process that greatly influences artifact management. Allowing “branching” from intermediate artifacts has the same effect.

3. Process influence

The development and support process also influences how artifacts are managed, as the promotion model below shows.

Artifact relationships

Managing versions of artifacts independently is tedious but not very complex. The complexity grows when the relations among artifacts must be controlled, such as:

  • Requirements ↔ test cases
  • Design elements ↔ logic code segments
  • Logic code segments ↔ database tables
  • UI screens ↔ code segments
  • Messages, help texts ↔ source code
  • Test cases ↔ logic code segments
  • Database tables ↔ initialization data

On top of that, one product may have several versions of its requirements: a general version, a variant for a special industry or customer, and country-specific versions (for example French or Japanese).

Configuration management framework

Software engineers must establish a framework to control all the piece parts of software artifacts. Policies and processes strongly influence it, and it has two main models: the naming model and the storage and access model.

Naming model

To control the pieces there must be identifiers. A naming model uniquely identifies each artifact and associates related items. It assumes a unique product name, multiple types and forms of artifacts (e.g. spreadsheets), at least two levels of grouping (versions within a release) and translated, multi-country releases.

Build and integration

The build and integration process converts and integrates source files into a set of executable files for a specific execution environment. It has two major steps.

CompileFix errors, resubmit
→
LinkWith external items
→
Test & debugFix and repeat

The build file controls the order of: dependency and cross-reference checking, compiling source into executables, linking the executables and generating any required data files.

Three types of build

Complete (nightly) build

  • With an automated tool, the build of a complex system is greatly eased: the tool processes the build cycle according to the build file.
  • For large, complex software a complete build can take more than 6 or 7 hours.
  • Because of that, builds are often run at night, hence “nightly builds”.

Partial build

  • During the test phase, bugs are found and fixed daily.
  • Not all source code is affected, so a complete rebuild is not needed.
  • Extreme care must be observed in partial builds.

Final build

  • When development is complete, a complete rebuild from the entire source is performed.
  • It must target the users’ run-time environment, not just the developers’.
  • Software that runs well on a developer’s system can still fail on a user’s because of environment differences.

SCM planning

Planning begins in the early coding phases of a project. Its outcome is the SCM plan (SCMP), which may be stretched or revised during the project. The SCMP can follow a public standard such as IEEE 828 or an organization’s own.

Documents

Defines the types of documents to be managed and a document naming scheme.

Responsibility

Defines who is responsible for the process and for the creation of baselines.

Policies

Fixes policies for version management and change control.

Tools & records

Defines the tools to use, and a configuration management database for recording configuration information.

SCM tools

Key features

Concurrency management

Concurrent operation means tasks happening at the same time. In SCM it means the same file being edited by multiple people at once.

Version control

Archives every change to a file, logs who made it, and lets you roll back to a previous version when something goes wrong.

Synchronization

Check out files or an entire repository copy, work on them, and check changes back in. Sync your local copy to stay current with teammates.

Software testing & quality assurance

Testing evaluates product quality, and improves it, by identifying defects and problems. Ideal processes, people, tools and conditions are rarely all met, so testing — along the way and at the end — is an ongoing process.

Software testing

A set of techniques for detecting and correcting errors in a software product.

Quality assurance (QA)

All activities designed to measure and improve quality in a product, including the whole process, training and preparation of the team.

Quality control (QC)

Activities that verify the quality of the product, detect faults or defects, and ensure defects are fixed prior to release.

Error → fault → failure

ErrorA mistake made by an engineer or programmer
→
FaultA condition that may cause a failure
→
FailureThe system cannot perform a function according to its specification

Verification

Checking that a software product conforms to its requirements and specifications.

Validation

Checking that the finished product meets the users’ requirements and specifications.

Purposes of testing

  • Find defects so they can be corrected or mitigated. The goal is to find faults, the more the better.
  • Give a general assessment of quality: some assurance the product works for many considered cases, and an estimate of the faults that may remain.

Error detection techniques

  • Testing
  • Inspections & reviews
  • Formal methods
  • Static analysis

Testing techniques: who, what, why, how

  • Programmers create and run test cases as they write code, to convince themselves it works.
  • Testers are technical people whose role is to write test cases and make sure they are executed.
  • Users help detect usability problems and expose the software to a broad range of real-world inputs.
  • Unit testing tests individual units, such as a single method or class.
  • Functional testing checks that units put together work as a functional unit.
  • Integration & system testing tests the integrated functionality of the complete system.
  • Acceptance: formal testing by the customer before accepting (and paying for) the product.
  • Conformance: testing against a set of standards or policies.
  • Configuration: combinations of software, databases and networks.
  • Performance: the program meets its performance specifications.
  • Stress: the program behaves correctly and degrades gracefully under stress.
  • Intuition or instinct.
  • Specification-based: from the specification alone, without looking at the code.
  • Coverage-based: define a measure of code coverage, then design test cases to reach it.
  • Regression: reuse the test cases from a previous version on the new version.

Test-design techniques

Equivalence-class partitioning

A specification-based, black-box technique that divides input into classes deemed equivalent for finding errors. If the program fails for one member of a class, expect it to fail for all; if it is correct for one, expect it to be correct for all.

Boundary value analysis

Uses the same classes but tests at the boundary, just inside it and just outside it. It may generate a high number of test cases.

Path analysis

A reproducible, traceable and countable technique, often white-box, where test cases come from the actual code or detailed design. It involves two tasks: analysis and determination.

Combination of conditions

Testing every combination is rarely practical, so generate just enough combinations to cover all pairs of values while keeping risk manageable.

Test-driven development & reviews

TDD is the practice of writing the unit tests before the code, then using them to make sure the code works. You first state the requirement as a test case, then implement it, which keeps you writing small pieces of code that are always covered by tests.

1. Write a testState the requirement
→
2. See it failRed
→
3. Make it passGreen
→
4. Re-run all testsNo regressions
→
5. RefactorMake it pretty

Writing valuable tests

  • GIVEN the initial conditions,
  • WHEN something occurs that needs testing,
  • THEN what is the expected response?

Keep tests short and to the point, so they describe the expected behavior of the unit.

Test each behavior once

  • Testing the same behavior twice does not make the software more likely to work.
  • If one change breaks twenty tests, you cannot tell what is broken. A single failing test makes the bug easy to find.
  • Each test must be independent of the others.

TDD in this project

The same idea, written with Jest (the lecture used pytest, JUnit and PHPUnit):

test("returns boundary, just inside and just outside values", () => {
  // GIVEN a valid range of 18 to 60
  // WHEN we ask for its boundary values
  // THEN we get the values around both boundaries
  expect(boundaryValues(18, 60)).toEqual([17, 18, 19, 59, 60, 61]);
});

Inspections and reviews

Having code reviewed by a team of developers is a cost-effective way to detect errors. Software inspections are detailed reviews of work in progress, following the steps developed by Michael Fagan at IBM:

  1. Planning: an inspection team and a moderator are designated, and materials are distributed days before the meeting.
  2. Overview: a walk-through of the work product (may be skipped if everyone is familiar with the project).
  3. Preparation: every inspector studies the work product thoroughly; checklists may help.
  4. Examination: a meeting where the inspectors review the product together.
  5. Rework: the author corrects all defects.
  6. Follow-up: the moderator checks the corrections, or the work is inspected again.

Formal methods

Mathematical techniques used to prove with absolute certainty that a program works, or that an implementation conforms to a specification. They take considerable effort to master and do not apply to all programs.

Static analysis

Examines the static structure of executable and non-executable files to find error-prone conditions. It is usually automatic, and a person reviews the results to remove false positives. The ESLint step in this site’s pipeline is static analysis.

    To recap

    • A large, complex software project requires proper management of all the artifacts it generates.
    • A configuration management framework has two models: the naming model and the storage and access model.
    • Coupled with the build and integration process, these let us manage software piece parts and produce different releases for users.
    • Producing high-quality software means detecting and correcting errors through verification, testing, inspections and reviews, formal methods and static analysis.
